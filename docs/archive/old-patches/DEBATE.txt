**Função `loadDrinks` — com tratamento diferenciado de erros:**
```typescript
async function loadDrinks() {
  setLoadingDrinks(true)
  setDrinksError(null)
  const supabase = createClient()

  // A aplicação depende exclusivamente de category_role = 'drinks'
  // Nunca usar o nome textual da categoria
  // limit(1) evita quebra caso mais de uma categoria esteja marcada como drinks
  // A unicidade por restaurante será implementada com a arquitetura multi-tenant
  const { data: categoryData, error: categoryError } = await supabase
    .from('categories')
    .select('id')
    .eq('category_role', 'drinks')
    .limit(1)
    .maybeSingle()

  if (categoryError) {
    console.error('[recepcao] Erro ao buscar categoria de bebidas:', categoryError)
    setDrinksError('Não foi possível carregar as bebidas.')
    setLoadingDrinks(false)
    return
  }

  if (!categoryData) {
    // Categoria não configurada — não é erro de banco
    console.warn('[recepcao] Nenhuma categoria com category_role = drinks encontrada.')
    setLoadingDrinks(false)
    return
  }

  const { data, error: itemsError } = await supabase
    .from('menu_items')
    .select('*') // substituir por campos reais após inspeção
    .eq('category_id', categoryData.id)
    .eq([coluna de disponibilidade real confirmada na inspeção], true)
    .order('name')

  if (itemsError) {
    console.error('[recepcao] Erro ao buscar bebidas:', itemsError)
    setDrinksError('Não foi possível carregar as bebidas.')
    setLoadingDrinks(false)
    return
  }

  // data vazio = categoria existe mas sem itens disponíveis — não é erro
  setDrinks(data ?? [])
  setLoadingDrinks(false)
}
```

Substituir `[coluna de disponibilidade real confirmada na inspeção]` pelo nome real encontrado.

**Função `handleConfirmDrink` — com try/catch obrigatório:**
```typescript
async function handleConfirmDrink(drink: MenuItem, qty: number) {
  setOrderState('submitting')
  setErrorMsg('')

  const { customerSessionId, tableSessionId, customer, context } = useSession.getState()

  try {
    const res = await fetch('/api/orders', {
      method: 'POST',
      headers: { 'Content-Type': 'application/json' },
      body: JSON.stringify({
        name: customer.name,
        table_num: context.tableNum || null,
        table_session_id: tableSessionId,
        customer_session_id: customerSessionId,
        created_by: 'customer',
        items: [{ id: drink.id, name: drink.name, price: drink.price, qty }],
        total: drink.price * qty,
      }),
    })

    if (!res.ok) {
      const text = await res.text()
      console.error('[recepcao] Erro HTTP ao enviar pedido:', res.status, text)
      setOrderState('error')
      setErrorMsg('Não foi possível enviar o pedido. Tente novamente.')
      return
    }

    const data = await res.json()
    const orderId = Number(data.id)

    // Usar o formato exato de CustomerOrder confirmado na inspeção
    const newOrder = {
      id: orderId,
      status: 'pending' as const,
      items: [{ id: drink.id, name: drink.name, price: drink.price, qty }],
      total: drink.price * qty,
      itemCount: qty,
      createdAt: data.created_at,
      tableNum: context.tableNum || null,
    }

    useOrderTracker.getState().addOrder(newOrder)
    useAccount.getState().addOrder(newOrder) // usar assinatura real confirmada na inspeção
    useSession.getState().setStatus('tracking')

    setConfirmedDrinkName(`${qty}x ${drink.name}`)
    setSelectedDrink(null)
    setQuantity(1)
    setOrderState('confirmed')

  } catch (err) {
    // Erro de rede ou exceção inesperada
    console.error('[recepcao] Exceção ao enviar pedido:', err)
    setOrderState('error')
    setErrorMsg('Erro de conexão. Verifique sua internet e tente novamente.')
  }
}
```

## WHITE_LABEL_SYSTEM.md — Análise crítica

### O que está sólido

**Seção 3 — Separação entre Produto e Restaurante:** este é o princípio mais importante do documento e está correto. Qualquer componente que hoje referencia `var(--parrilla-red)` ou textos como "Parrilla" hardcoded viola esse princípio. O documento cria o contrato certo.

**Seção 14 — Category Roles:** decisão excelente, já parcialmente implementada no PATCH 11A com `category_role`. O documento expande corretamente para `featured`, `wine`, `happy_hour`, `seasonal` — isso é necessário para SaaS.

**Seção 18 — White Label como configuração, não desenvolvimento:** esse é o objetivo correto e o mais difícil de atingir. Merece ser detalhado em documento próprio (`RESTAURANT_CONFIG.md`), que o próprio documento sugere ao final.

---

### Problemas e riscos

**Problema 1 — Theme System sem contrato técnico**

A Seção 6 lista os tokens (`theme.primary`, `theme.background`, etc.) mas não define:
- Onde esse objeto `theme` vive no código
- Como é carregado por restaurante
- Se é injetado via CSS variables, via React Context, via arquivo de configuração ou via banco de dados
- Quem é responsável por fornecer o tema em runtime

Sem isso, cada desenvolvedor vai implementar `theme` de forma diferente. O risco concreto: o código atual usa `var(--parrilla-red)` em dezenas de arquivos. A migração para `var(--color-primary)` precisa de um plano de execução, não apenas de uma declaração de intenção.

**Recomendação:** adicionar uma seção "Implementação do Theme System" que define explicitamente: os tokens são CSS custom properties (`--color-primary`, `--color-background`, etc.) injetadas por um arquivo de tema por restaurante. O mapeamento entre o nome semântico do token e o valor concreto acontece em `themes/[restaurantId].css` ou equivalente.

---

**Problema 2 — Experience Engine descrito mas não modelado**

A Seção 13 descreve etapas de experiência como sequência linear. Mas restaurantes diferentes podem ter sequências diferentes — um bar pode pular "Boas-vindas" e ir direto para "Oferta de bebidas". Uma cafeteria pode não ter "Mesa" como conceito central.

O documento diz que "o motor apenas renderiza a configuração" mas não define:
- Qual é o formato dessa configuração
- Quem a define (banco de dados? arquivo JSON? painel admin?)
- Como o motor interpreta e navega entre etapas
- Como lida com etapas condicionais ("se cliente recorrente, pular onboarding")

Isso é um gap crítico. Sem essa especificação, o PATCH 13 (Experiência Guiada) vai ser implementado como código procedural em vez de configuração declarativa — e vai precisar ser reescrito quando o segundo restaurante chegar.

**Recomendação:** criar `EXPERIENCE_ENGINE.md` como documento separado antes de implementar qualquer patch de experiência guiada. Esse documento deve modelar o formato da configuração de experiência como dado, não como código.

---

**Problema 3 — Restaurant Config existe como lista, não como schema**

A Seção 12 lista o que pertence ao restaurante (nome, logo, tema, etc.) mas não define a estrutura de dados. Para um SaaS isso é crítico — a configuração precisa de um schema versionado que permita adicionar campos sem quebrar restaurantes existentes.

**Recomendação:** `RESTAURANT_CONFIG.md` deve definir o schema completo com tipos, valores padrão e campos obrigatórios vs opcionais.

---

**Problema 4 — Multi-tenant sem definição de isolamento**

O documento afirma que o sistema suportará múltiplos restaurantes mas não define:
- Como os dados são isolados no banco (`restaurant_id` em todas as tabelas? Row Level Security por restaurante?)
- Como o sistema sabe qual restaurante está servindo em runtime (subdomínio? URL? QR Code com identificador?)
- Como o tema do restaurante correto é carregado

Sem isso, qualquer tabela criada sem `restaurant_id` é uma dívida que vai custar caro quando o segundo restaurante chegar. `categories` já recebeu `category_role` — mas não tem `restaurant_id`.

**Recomendação:** adicionar uma seção "Modelo de Multi-tenancy" que define o identificador de restaurante, o mecanismo de isolamento de dados e o mecanismo de carregamento de tema.

## DESIGN_SYSTEM.md — Análise crítica

### O que está sólido

**Seção 2 — Cinco princípios:** Clareza, Hierarquia, Pouco Ruído, Rapidez e Emoção são princípios acionáveis. Qualquer decisão de UI pode ser testada contra eles.

**Seção 4 — Design Tokens:** correto e consistente com o WHITE_LABEL_SYSTEM. A lista de tokens de cores, radius, shadows e spacing é suficiente para V1.

**Seção 21 — Fator Uau:** este é o princípio mais diferenciador. A pergunta "existe algum detalhe que faria o cliente comentar sobre isso?" deve estar em cada revisão de PATCH de produto.

---

### Problemas e riscos

**Problema 1 — Tokens definidos mas sem valores de referência**

O documento lista os tokens mas não fornece os valores concretos para o restaurante de referência (+54 Parrilla). Sem isso, o Gemini vai continuar usando `var(--parrilla-red)` porque é o que existe no código hoje.

A migração precisa de uma tabela de equivalência:

| Token semântico | Valor +54 Parrilla | Tipo |
|---|---|---|
| `--color-primary` | `#c0392b` | Cor de ação principal |
| `--color-background` | `#0e0e0e` | Fundo base |
| `--color-surface` | `#171717` | Superfície de cards |
| `--color-border` | `#2a2a2a` | Bordas |
| `--color-text-primary` | `#f0ede8` | Texto principal |
| `--color-text-muted` | `#7a7570` | Texto secundário |
| `--color-accent` | `#e67e22` | Preços, destaques |

Sem essa tabela, o Design System é uma intenção, não uma especificação.

---

**Problema 2 — Sete tipos de botão descritos como cinco**

A Seção 7 diz "existem apenas cinco botões" e lista Primary, Secondary, Ghost, Danger, Floating. Mas no código atual existem variações não documentadas — botões com `opacity: 0.7` quando disabled, botões com `pointerEvents: none`, botões com `border: 1px solid` como outline. Essas variações precisam ser mapeadas como estados, não como tipos novos.

**Recomendação:** cada tipo de botão deve ter seus estados documentados: Default, Hover, Pressed, Disabled, Loading. Isso é o que permite ao Gemini implementar consistentemente sem inventar variações.

---

**Problema 3 — Motion sem valores concretos para os estados do restaurante**

A Seção 12 define durations (150ms, 250ms, 350ms) mas a Seção 16 do WHITE_LABEL_SYSTEM define que animações comunicam estado (pedido enviado, pedido aceito, etc.). Esses dois documentos precisam se conectar: qual duração para qual estado? Qual curva de easing? Qual tipo de animação (fade, slide, scale)?

Sem isso, cada desenvolvedor vai inventar animações diferentes para o mesmo estado.

---

**Problema 4 — Performance Percebida sem especificação de Skeleton**

A Seção 17 menciona Skeleton como estratégia mas não define como o skeleton do Parrilla OS deve se parecer. Skeletons implementados sem padrão ficam visualmente inconsistentes — alguns pulsam, outros não, alguns têm bordas, outros não.

async function handleConfirmDrink(drink: MenuItem, qty: number) {
  setOrderState('submitting')
  setErrorMsg('')

  const { customerSessionId, tableSessionId, customer, context } = useSession.getState()

  const res = await fetch('/api/orders', {
    method: 'POST',
    headers: { 'Content-Type': 'application/json' },
    body: JSON.stringify({
      name: customer.name,
      table_num: context.tableNum || null,
      table_session_id: tableSessionId,
      customer_session_id: customerSessionId,
      created_by: 'customer',
      items: [{ id: drink.id, name: drink.name, price: drink.price, qty }],
      total: drink.price * qty,
    }),
  })

  if (!res.ok) {
    setOrderState('error')
    setErrorMsg('Não foi possível enviar o pedido. Tente novamente.')
    return
  }

  const data = await res.json()
  const orderId = Number(data.id)

  // Formato exato de CustomerOrder confirmado na inspeção
  const newOrder = {
    id: orderId,
    status: 'pending' as const,
    items: [{ id: drink.id, name: drink.name, price: drink.price, qty }],
    total: drink.price * qty,
    itemCount: qty,
    createdAt: data.created_at,
    tableNum: context.tableNum || null,
  }

  useOrderTracker.getState().addOrder(newOrder)
  useAccount.getState().addOrder(newOrder)  // usar assinatura real confirmada na inspeção
  useSession.getState().setStatus('tracking')

  setConfirmedDrinkName(`${qty}x ${drink.name}`)
  setSelectedDrink(null)
  setQuantity(1)
  setOrderState('confirmed')
}

O prompt está muito bem estruturado, mas ainda tem dois bugs funcionais importantes antes de enviar ao Gemini:

Os botões de quantidade estão dentro de um card clicável
O card possui onClick que faz:

selecionar a bebida;

redefinir a quantidade para 1.

Ao clicar em +, − ou Confirmar, o clique pode subir para o card e executar esse onClick novamente. Resultado possível: a quantidade volta para 1 ou o estado muda de forma inesperada.

Acrescente:

Nos botões −, + e Confirmar, usar event.stopPropagation() antes da ação. O clique nos controles internos não pode disparar o onClick do card.

Falta proteção contra erro de rede no pedido
fetch() pode lançar exceção antes de existir uma resposta HTTP. Hoje isso deixaria o estado preso em submitting.

Acrescente:

Envolver todo o envio de handleConfirmDrink em try/catch/finally ou tratamento equivalente. Em erro de rede:

definir orderState = 'error';

exibir mensagem genérica;

registrar o erro real no console;

garantir que o botão possa ser usado novamente.

Ajuste recomendado

Como categories poderá ter mais de uma categoria marcada como drinks futuramente, não convém depender de .maybeSingle() sem garantir unicidade.

Para esta V1, determine uma destas estratégias:

aplicar .limit(1).maybeSingle(); ou

criar regra de unicidade por restaurante quando o multi-tenant for implementado.

Hoje, com uma única unidade, .limit(1) evita quebra acidental se duas categorias forem marcadas.

async function loadDrinks() {
  setLoadingDrinks(true)
  setDrinksError(null)
  const supabase = createClient()

  // A aplicação depende exclusivamente de category_role = 'drinks'
  // Nunca usar o nome textual da categoria
  // limit(1) evita quebra caso mais de uma categoria esteja marcada como drinks
  // A unicidade por restaurante será implementada com a arquitetura multi-tenant
  const { data: categoryData, error: categoryError } = await supabase
    .from('categories')
    .select('id')
    .eq('category_role', 'drinks')
    .limit(1)
    .maybeSingle()

  if (categoryError) {
    console.error('[recepcao] Erro ao buscar categoria de bebidas:', categoryError)
    setDrinksError('Não foi possível carregar as bebidas.')
    setLoadingDrinks(false)
    return
  }

  if (!categoryData) {
    // Categoria não configurada — não é erro de banco
    console.warn('[recepcao] Nenhuma categoria com category_role = drinks encontrada.')
    setLoadingDrinks(false)
    return
  }

  const { data, error: itemsError } = await supabase
    .from('menu_items')
    .select('*') // substituir por campos reais após inspeção
    .eq('category_id', categoryData.id)
    .eq([coluna de disponibilidade real confirmada na inspeção], true)
    .order('name')

  if (itemsError) {
    console.error('[recepcao] Erro ao buscar bebidas:', itemsError)
    setDrinksError('Não foi possível carregar as bebidas.')
    setLoadingDrinks(false)
    return
  }

  // data vazio = categoria existe mas sem itens disponíveis — não é erro
  setDrinks(data ?? [])
  setLoadingDrinks(false)
}

async function handleConfirmDrink(drink: MenuItem, qty: number) {
  setOrderState('submitting')
  setErrorMsg('')

  const { customerSessionId, tableSessionId, customer, context } = useSession.getState()

  try {
    const res = await fetch('/api/orders', {
      method: 'POST',
      headers: { 'Content-Type': 'application/json' },
      body: JSON.stringify({
        name: customer.name,
        table_num: context.tableNum || null,
        table_session_id: tableSessionId,
        customer_session_id: customerSessionId,
        created_by: 'customer',
        items: [{ id: drink.id, name: drink.name, price: drink.price, qty }],
        total: drink.price * qty,
      }),
    })

    if (!res.ok) {
      const text = await res.text()
      console.error('[recepcao] Erro HTTP ao enviar pedido:', res.status, text)
      setOrderState('error')
      setErrorMsg('Não foi possível enviar o pedido. Tente novamente.')
      return
    }

    const data = await res.json()
    const orderId = Number(data.id)

    // Usar o formato exato de CustomerOrder confirmado na inspeção
    const newOrder = {
      id: orderId,
      status: 'pending' as const,
      items: [{ id: drink.id, name: drink.name, price: drink.price, qty }],
      total: drink.price * qty,
      itemCount: qty,
      createdAt: data.created_at,
      tableNum: context.tableNum || null,
    }

    useOrderTracker.getState().addOrder(newOrder)
    useAccount.getState().addOrder(newOrder) // usar assinatura real confirmada na inspeção
    useSession.getState().setStatus('tracking')

    setConfirmedDrinkName(`${qty}x ${drink.name}`)
    setSelectedDrink(null)
    setQuantity(1)
    setOrderState('confirmed')

  } catch (err) {
    // Erro de rede ou exceção inesperada
    console.error('[recepcao] Exceção ao enviar pedido:', err)
    setOrderState('error')
    setErrorMsg('Erro de conexão. Verifique sua internet e tente novamente.')
  }
}

Análise Crítica — WHITE_LABEL_SYSTEM.md e DESIGN_SYSTEM.md
Avaliação geral
Os dois documentos estabelecem uma visão correta e ambiciosa. O princípio de separação entre Produto e Restaurante é arquiteturalmente sólido e é exatamente o que diferencia um SaaS de um sistema customizado. Minha análise vai apontar onde a visão está completa, onde está incompleta e onde existe risco real de implementação.

WHITE_LABEL_SYSTEM.md — Análise crítica
O que está sólido
Seção 3 — Separação entre Produto e Restaurante: este é o princípio mais importante do documento e está correto. Qualquer componente que hoje referencia var(--parrilla-red) ou textos como "Parrilla" hardcoded viola esse princípio. O documento cria o contrato certo.

Seção 14 — Category Roles: decisão excelente, já parcialmente implementada no PATCH 11A com category_role. O documento expande corretamente para featured, wine, happy_hour, seasonal — isso é necessário para SaaS.

Seção 18 — White Label como configuração, não desenvolvimento: esse é o objetivo correto e o mais difícil de atingir. Merece ser detalhado em documento próprio (RESTAURANT_CONFIG.md), que o próprio documento sugere ao final.

Problemas e riscos
Problema 1 — Theme System sem contrato técnico

A Seção 6 lista os tokens (theme.primary, theme.background, etc.) mas não define:

Onde esse objeto theme vive no código
Como é carregado por restaurante
Se é injetado via CSS variables, via React Context, via arquivo de configuração ou via banco de dados
Quem é responsável por fornecer o tema em runtime
Sem isso, cada desenvolvedor vai implementar theme de forma diferente. O risco concreto: o código atual usa var(--parrilla-red) em dezenas de arquivos. A migração para var(--color-primary) precisa de um plano de execução, não apenas de uma declaração de intenção.

Recomendação: adicionar uma seção "Implementação do Theme System" que define explicitamente: os tokens são CSS custom properties (--color-primary, --color-background, etc.) injetadas por um arquivo de tema por restaurante. O mapeamento entre o nome semântico do token e o valor concreto acontece em themes/[restaurantId].css ou equivalente.

Problema 2 — Experience Engine descrito mas não modelado

A Seção 13 descreve etapas de experiência como sequência linear. Mas restaurantes diferentes podem ter sequências diferentes — um bar pode pular "Boas-vindas" e ir direto para "Oferta de bebidas". Uma cafeteria pode não ter "Mesa" como conceito central.

O documento diz que "o motor apenas renderiza a configuração" mas não define:

Qual é o formato dessa configuração
Quem a define (banco de dados? arquivo JSON? painel admin?)
Como o motor interpreta e navega entre etapas
Como lida com etapas condicionais ("se cliente recorrente, pular onboarding")
Isso é um gap crítico. Sem essa especificação, o PATCH 13 (Experiência Guiada) vai ser implementado como código procedural em vez de configuração declarativa — e vai precisar ser reescrito quando o segundo restaurante chegar.

Recomendação: criar EXPERIENCE_ENGINE.md como documento separado antes de implementar qualquer patch de experiência guiada. Esse documento deve modelar o formato da configuração de experiência como dado, não como código.

Problema 3 — Restaurant Config existe como lista, não como schema

A Seção 12 lista o que pertence ao restaurante (nome, logo, tema, etc.) mas não define a estrutura de dados. Para um SaaS isso é crítico — a configuração precisa de um schema versionado que permita adicionar campos sem quebrar restaurantes existentes.

Recomendação: RESTAURANT_CONFIG.md deve definir o schema completo com tipos, valores padrão e campos obrigatórios vs opcionais.

Problema 4 — Multi-tenant sem definição de isolamento

O documento afirma que o sistema suportará múltiplos restaurantes mas não define:

Como os dados são isolados no banco (restaurant_id em todas as tabelas? Row Level Security por restaurante?)
Como o sistema sabe qual restaurante está servindo em runtime (subdomínio? URL? QR Code com identificador?)
Como o tema do restaurante correto é carregado
Sem isso, qualquer tabela criada sem restaurant_id é uma dívida que vai custar caro quando o segundo restaurante chegar. categories já recebeu category_role — mas não tem restaurant_id.

Recomendação: adicionar uma seção "Modelo de Multi-tenancy" que define o identificador de restaurante, o mecanismo de isolamento de dados e o mecanismo de carregamento de tema.

DESIGN_SYSTEM.md — Análise crítica
O que está sólido
Seção 2 — Cinco princípios: Clareza, Hierarquia, Pouco Ruído, Rapidez e Emoção são princípios acionáveis. Qualquer decisão de UI pode ser testada contra eles.

Seção 4 — Design Tokens: correto e consistente com o WHITE_LABEL_SYSTEM. A lista de tokens de cores, radius, shadows e spacing é suficiente para V1.

Seção 21 — Fator Uau: este é o princípio mais diferenciador. A pergunta "existe algum detalhe que faria o cliente comentar sobre isso?" deve estar em cada revisão de PATCH de produto.

Problemas e riscos
Problema 1 — Tokens definidos mas sem valores de referência

O documento lista os tokens mas não fornece os valores concretos para o restaurante de referência (+54 Parrilla). Sem isso, o Gemini vai continuar usando var(--parrilla-red) porque é o que existe no código hoje.

A migração precisa de uma tabela de equivalência:

Token semântico	Valor +54 Parrilla	Tipo
--color-primary
#c0392b	Cor de ação principal
--color-background
#0e0e0e	Fundo base
--color-surface
#171717	Superfície de cards
--color-border
#2a2a2a	Bordas
--color-text-primary
#f0ede8	Texto principal
--color-text-muted
#7a7570	Texto secundário
--color-accent
#e67e22	Preços, destaques
Sem essa tabela, o Design System é uma intenção, não uma especificação.

Problema 2 — Sete tipos de botão descritos como cinco

A Seção 7 diz "existem apenas cinco botões" e lista Primary, Secondary, Ghost, Danger, Floating. Mas no código atual existem variações não documentadas — botões com opacity: 0.7 quando disabled, botões com pointerEvents: none, botões com border: 1px solid como outline. Essas variações precisam ser mapeadas como estados, não como tipos novos.

Recomendação: cada tipo de botão deve ter seus estados documentados: Default, Hover, Pressed, Disabled, Loading. Isso é o que permite ao Gemini implementar consistentemente sem inventar variações.

Problema 3 — Motion sem valores concretos para os estados do restaurante

A Seção 12 define durations (150ms, 250ms, 350ms) mas a Seção 16 do WHITE_LABEL_SYSTEM define que animações comunicam estado (pedido enviado, pedido aceito, etc.). Esses dois documentos precisam se conectar: qual duração para qual estado? Qual curva de easing? Qual tipo de animação (fade, slide, scale)?

Sem isso, cada desenvolvedor vai inventar animações diferentes para o mesmo estado.

Problema 4 — Performance Percebida sem especificação de Skeleton

A Seção 17 menciona Skeleton como estratégia mas não define como o skeleton do Parrilla OS deve se parecer. Skeletons implementados sem padrão ficam visualmente inconsistentes — alguns pulsam, outros não, alguns têm bordas, outros não.

O que está faltando nos dois documentos
1. RESTAURANT_CONFIG.md — schema completo do que cada restaurante pode configurar, com tipos e valores padrão. Sugerido pelos próprios documentos mas não criado.

2. EXPERIENCE_ENGINE.md — formato de configuração das etapas de experiência. Crítico antes do PATCH 13.

3. MIGRATION_GUIDE.md — plano de migração do código atual (que usa var(--parrilla-red), textos hardcoded e lógica acoplada ao +54) para a arquitetura white label. Sem esse guia, os dois documentos acima ficam como visão sem execução.

4. COMPONENT_LIBRARY.md — especificação dos componentes universais listados na Seção 11 do WHITE_LABEL_SYSTEM (Button, Card, Drawer, etc.) com suas props, estados e comportamentos. Isso é o que transforma o Design System de documento em código.

DESIGN REVIEW V1 — Parrilla OS × +54 Parrilla
1. Primeira impressão
Cinco segundos olhando a imagem e dois sentimentos distintos aparecem simultaneamente.

O restaurante transmite calor. Literalmente. Carne na brasa, madeira escura, luz âmbar, ambiente aconchegante com mesas de couro marrom, plantas, pé-direito alto com vigas aparentes. As fotos de comida têm aquela qualidade de vapor subindo, de gordura reluzindo sob luz quente. O cardápio físico deles usa fundo preto com tipografia serifada em dourado/creme — estética de steakhouse premium argentino.

O sistema atual transmite eficiência. Interface dark bem construída, limpa, funcional. Mas fria. O vermelho escolhido (
#c0392b) é um vermelho de alerta, não um vermelho de brasa. O fundo é um preto neutro, não um preto de carvão. A tipografia é sans-serif contemporânea — resolve bem legibilidade mas não carrega personalidade gastronômica.

A distância entre os dois não é enorme — o dark mode acerta a direção. Mas é a diferença entre um restaurante premium e o app de pedido desse restaurante.

2. Comparação Restaurante × Sistema
Onde combinam
Tom escuro: o restaurante vive no escuro elegante — ambiente com iluminação pontual, madeira escura, couro escuro. O dark mode do sistema está certo. Mudar para claro seria um erro grave.

Identidade forte: o "+54" como identificador numérico é poderoso. O sistema já usa isso no header. Essa decisão está correta e deve ser preservada.

Foco no produto: as fotos do Instagram são todas close em comida, sem filtros exagerados. O sistema não polui com elementos desnecessários. Essa contenção visual está alinhada.

Onde entram em conflito
Temperatura das cores: o restaurante vive em âmbar, dourado, ocre, marrom quente. O sistema usa vermelho frio e cinza neutro. São paletas de temperatura opostas — o restaurante é warm, o sistema é cool.

Tipografia: o cardápio físico do +54 usa serifa elegante para títulos (visível nos stories do Instagram — "CARDÁPIO (+54) PARRILLA" em fonte serifada com personalidade). O sistema usa sans-serif genérica. Não é errado, mas não carrega o DNA.

O vermelho: o vermelho atual lembra botão de "deletar" de sistema administrativo. O restaurante usa um tom mais quente, próximo de vinho tinto envelhecido, não de sinalização de perigo.

Textura vs planura: o ambiente físico tem textura em tudo — madeira com veios, couro com costura, tijolos, plantas. O sistema é completamente plano. Um toque sutil de textura (não literalmente, mas na linguagem visual) faria diferença.

Preço como destaque: nos stories do cardápio, os preços aparecem com destaque em dourado/âmbar. No sistema o preço está em --parrilla-ember (laranja) que é a decisão mais próxima do certo — mas a intensidade poderia ser maior.

3. O DNA do +54 Parrilla
Se o restaurante fosse uma pessoa, seria um sommelier argentino de 55 anos que trabalha naquele restaurante há 20 anos.

Ele fala com calma, com acento, com precisão. Não usa palavras desnecessárias. Quando recomenda um vinho, é porque conhece. Não tenta impressionar — impressiona sem tentar.

Ele pisa devagar, com propósito. Nunca corre. Mas quando você precisa dele, está lá.

Ele cumprimenta pelo nome se você já esteve lá antes. Na primeira vez, é caloroso mas discreto — não invasivo.

Ele serve um vinho sem fazer cerimônia exagerada, mas com um pequeno detalhe que você nota: a temperatura está perfeita, a taça está seca, ele espera você provar antes de servir.

Ele entrega a conta numa pasta de couro sem dizer o valor em voz alta. Discreto. Digno.

Ele pede desculpas por um atraso olhando nos olhos, sem inventar desculpa, oferecendo algo concreto. Sem dramaturgia.

Palavras que definem o DNA:

Argentino (não genérico sul-americano)
Carne, brasa, parrilla (não "comida")
Caloroso mas não exuberante
Premium sem ser intimidador
Masculino mas acolhedor
Artesanal mas preciso
Escuro, âmbar, quente
4. O DNA que o Parrilla OS deveria transmitir
O sistema não deve tentar ser o restaurante. Deve ser a extensão digital do garçom daquele restaurante.

Deve transmitir:

Confiança silenciosa. Não precisa gritar que é bom. É evidente.

Calor contido. Não é um app de delivery frio. Há uma presença humana por trás — alguém que preparou aquela experiência para você.

Precisão argentina. As coisas estão no lugar certo. Os preços estão certos. O pedido vai chegar.

Escuridão fértil. Não o preto de tela apagada. O preto de carvão aceso, de brasa que vai começar a trabalhar. O escuro que antecipa algo quente.

5. As 20 maiores diferenças (da mais para a menos importante)
1. Temperatura da paleta: o sistema é cool, o restaurante é warm. Esta é a maior distância emocional.

2. O vermelho:
#c0392b é vermelho de alerta. O restaurante pede um vermelho de brasa — mais para
#9B2335 (vinho escuro) ou um tom entre vermelho e ocre queimado.

3. Ausência de âmbar/dourado como cor principal de destaque: o accent atual (laranja
#e67e22) está na direção certa mas claro demais. Precisaria ser mais rico, mais quente, mais "cobre envelhecido".

4. Tipografia sem personalidade gastronômica: uma fonte serifada para títulos e display (não para corpo de texto, que permanece sans-serif para legibilidade) mudaria completamente a percepção.

5. Fundo sem profundidade:
#0e0e0e é preto neutro. Um preto levemente aquecido (
#0f0d0b — com leve tonalidade marrom) aproximaria do ambiente físico sem sacrificar contraste.

6. Cards sem elevação percebida: os cards atuais usam border de 1px como única diferenciação. Um leve calor na cor de fundo do card (
#1a1714 em vez de
#1c1c1c) criaria profundidade visual.

7. Botão primário parece sistema: o CTA principal precisa comunicar ação gastronômica, não submit de formulário. Forma e peso importam tanto quanto cor.

8. Ausência de hierarquia tipográfica clara: nome do prato, descrição e preço têm pesos próximos. A diferença entre eles deveria ser mais dramática.

9. Preço não celebrado: num restaurante premium o preço não é escondido mas também não é agressivo. No sistema ele aparece igual a qualquer outro texto. Poderia ter mais presença.

10. Logo "+54" poderia ter mais caráter: atualmente é texto puro. Uma micro-decisão tipográfica (tracking, peso, proporção) faria diferença.

11. Ícones genéricos: os emojis usados (🥩, 🍺) funcionam mas não têm identidade. Ícones customizados ou uma família consistente elevariam o produto.

12. Estados de loading sem personalidade: o "Carregando..." é completamente genérico. Uma mensagem com voz do restaurante ("Preparando seu cardápio...") mudaria o tom.

13. Mensagens de erro sem voz: "Não foi possível carregar" é linguagem de sistema. O restaurante falaria diferente.

14. Botão "Continuar" como label genérica: em cada tela o CTA poderia ter uma voz específica que contextualiza a ação.

15. Ausência de separadores com personalidade: os border: 1px solid são funcionais mas invisíveis. Uma linha mais fina, em cor levemente aquecida, com espaçamento generoso, communicaria elegância.

16. Espaçamento interno dos cards: ligeiramente apertado para um produto premium. Mais espaço interno transmite mais valor.

17. Barra de navegação de categorias: pills/chips com borda parecem tabs de sistema. Uma linha inferior como indicador de seleção seria mais elegante.

18. Header muito funcional: o header atual é correto mas não tem presença. Poderia ter mais height e respiração.

19. Ausência de fotografia integrada: o restaurante é altamente visual (ver Instagram). O sistema atual não usa nenhuma imagem ambiental ou de atmosfera.

20. Confirmações sem emoção: "Pedido enviado" poderia ser um momento de pequena celebração visual, não apenas uma mensagem funcional.

6. Melhorias de maior impacto
Estas cinco mudanças, sem alterar fluxo ou arquitetura, elevariam drasticamente a percepção:

1. Trocar a paleta de cores para warm dark
Fundo de
#0e0e0e para
#0f0d0b. Vermelho de
#c0392b para
#8B1A2B. Accent de
#e67e22 para
#C17F3A. Superfície de
#171717 para
#1a1714. Isso sozinho muda a temperatura emocional do produto inteiro.

2. Adicionar uma fonte serifada para display
Apenas para h1, títulos de seção e o "+54". O corpo permanece sans-serif. Uma fonte como Playfair Display, Cormorant Garamond ou DM Serif Display carregaria imediatamente o DNA gastronômico. É uma linha no CSS, não uma refatoração.

3. Dar mais presença ao preço
Aumentar o tamanho, mudar para a cor accent e adicionar font-variant-numeric: tabular-nums com um peso acima do texto de descrição. O preço num restaurante premium não se esconde — ele justifica a experiência.

4. Reescrever os microtextos com a voz do restaurante
"Carregando..." → "Preparando seu cardápio..."
"Confirmar pedido" → "Enviar para a cozinha"
"Pedido enviado" → "Seu pedido está nas mãos da nossa cozinha."
"Pedir conta" → "Solicitar a conta"
Zero esforço técnico. Impacto emocional enorme.

5. Aumentar o espaçamento interno de todos os cards
De padding: 14px para padding: 18px 20px. Mais ar = mais valor percebido. Uma das maneiras mais baratas de parecer premium.

7. O que manter
Dark mode: absolutamente correto para o DNA do restaurante. Não mudar.

Cantos retos (border-radius: 2px): a decisão de usar cantos quase retos em vez de pills arredondadas está certa. Combina com a estética industrial/rústica da parrilla.

Estrutura de dois drawers independentes: CartDrawer à direita, SessionDrawer à esquerda. É uma decisão UX correta e diferenciada.

O "+54" como identidade principal no header: usar o número como ancora visual é um insight de identidade forte. Manter.

Hierarquia de informação nos cards: nome → descrição → preço → ação. A ordem está certa.

Sem bordas arredondadas exageradas: o produto não deve parecer um app de delivery de massa. A contenção formal está correta.

8. Plano de evolução visual

Foto de ambiente na tela de boas-vindas
Possível vídeo curto de brasa/cozinha na tela de identificação
9. Pensando no futuro SaaS
Cada sugestão acima foi deliberadamente desacoplada do +54 Parrilla:

Sugestão	Reutilizável?	Como tornar reutilizável
Paleta warm dark	Sim	Tokens no theme.[restaurantId] — cada restaurante define seus valores
Fonte serifada para display	Sim	theme.fontDisplay configurável por restaurante
Microtextos com voz	Sim	config.copy.[key] por restaurante — strings configuráveis, não hardcoded
Padding de cards	Sim	Token spacing.cardPadding no design system

Foto de ambiente	Sim	config.assets.ambientPhoto por restaurante
A regra que emerge é: qualquer elemento visual que hoje está hardcoded no componente deve migrar para um token ou configuração de restaurante. O componente renderiza. O restaurante decide como parece.

As fotos são consistentemente quentes. Carnes com crosta dourada em superfície de grelha escura. Massas com molho avermelhado. Café com espuma cremosa. Uma cerveja Brahma gelada. Um close de corte de carne com textura visível. Uma taça de vinho tinto.

A iluminação é sempre de baixo para cima ou lateral — cria volume, sombra, profundidade. Nunca flash frontal. Nunca fundo branco de estúdio. O ambiente das fotos é sempre escuro com o prato iluminado.

Temperatura de cor dominante: 2800K–3200K. Luz de vela, luz âmbar, luz incandescente. Nunca luz fria.

Stories do cardápio físico
Fundo preto absoluto. Tipografia em creme/off-white — não branco puro. O nome da unidade ("Cardápio (+54) PARRILLA Itaim Bibi") usa uma combinação de sans-serif condensada em caixa alta para "(+54) PARRILLA" e uma fonte cursiva/script para "Itaim Bibi". O cardápio de itens usa tipografia menor, muito espaçada, em creme sobre preto — elegante e legível.

Não existe vermelho no cardápio físico deles. Esta é a observação mais importante. O restaurante físico não usa vermelho como cor de marca. Usa preto, creme e a cor natural da comida.

Foto do ambiente — Unidade Aquarius
Esta foto muda tudo. O ambiente é completamente diferente do que eu esperaria de uma parrilla escura e rústica.

O espaço é contemporâneo e luminoso durante o dia. Paredes em tom petróleo/verde-azulado escuro. Madeira clara nas mesas e cadeiras. Cadeiras estofadas em couro natural (marrom caramelo). Plantas verdes abundantes. Pé-direito alto com vigas de madeira aparente. Luz natural abundante pelas janelas.

À noite o ambiente muda de temperatura completamente — a iluminação pontual cria o calor âmbar. Mas a identidade de dia é mais sofisticada e contemporânea do que rústica.

O restaurante é dual: rústico argentino nas referências de produto (carne, brasa, parrilla), contemporâneo e sofisticado no espaço físico.

3. Tipografia — Baseada em Evidências
O cardápio físico revela duas famílias:

Display/Marca: a escrita cursiva em "Itaim Bibi" e no nome das unidades usa uma fonte script elegante, com personalidade italiana/argentina. Referências próximas: Playfair Display Italic, Cormorant Garamond Italic, EB Garamond.

Corpo/Cardápio: a listagem de itens usa uma fonte sans-serif condensada, com muito tracking (espaçamento entre letras). Próxima de Montserrat, Raleway ou a própria fonte atual do sistema.

Números/Preços: os preços no cardápio físico aparecem em peso leve, alinhados à direita, com separação clara do nome do prato. Sugerem font-variant-numeric: tabular-nums com peso regular — não bold.

4. Materialidade e Textura
O restaurante não tem textura literal na identidade digital (cardápio é limpo). Mas a textura aparece na linguagem e na fotografia.

Para o sistema, textura não significa gradiente ou noise. Significa:

Profundidade entre camadas — background levemente diferente de surface, diferente de surface elevated
Calor nas bordas — borders levemente aquecidos (
#2A2520) em vez de cinza neutro
Sombras quentes — box-shadow com tom âmbar suavíssimo em vez de preto puro

Alterações em app/layout.tsx
Contexto: o Next.js 15 com next/font/google injeta fontes de forma otimizada — sem requisição externa em runtime, com fallback automático e exposição via CSS variable.

Passo 1 — Adicionar imports de fonte no topo do arquivo:

typescript
import { Cormorant_Garamond, Inter } from 'next/font/google'

const displayFont = Cormorant_Garamond({
  subsets: ['latin'],
  weight: ['400', '600'],
  style: ['normal', 'italic'],
  variable: '--font-display',
  display: 'swap',
})

const bodyFont = Inter({
  subsets: ['latin'],
  weight: ['400', '500', '600'],
  variable: '--font-body',
  display: 'swap',
})
Passo 2 — Aplicar as variáveis no elemento <html> ou <body>:

Localizar o elemento raiz do JSX retornado. Adicionar as classes das fontes:

typescript
<html lang="pt-BR" className={`${displayFont.variable} ${bodyFont.variable}`}>
Se já existir className no <html>, concatenar com espaço. Não remover classes existentes.

## 1. Primeira impressão

Cinco segundos olhando a imagem e dois sentimentos distintos aparecem simultaneamente.

O restaurante transmite **calor**. Literalmente. Carne na brasa, madeira escura, luz âmbar, ambiente aconchegante com mesas de couro marrom, plantas, pé-direito alto com vigas aparentes. As fotos de comida têm aquela qualidade de vapor subindo, de gordura reluzindo sob luz quente. O cardápio físico deles usa fundo preto com tipografia serifada em dourado/creme — estética de *steakhouse* premium argentino.

O sistema atual transmite **eficiência**. Interface dark bem construída, limpa, funcional. Mas fria. O vermelho escolhido (`#c0392b`) é um vermelho de alerta, não um vermelho de brasa. O fundo é um preto neutro, não um preto de carvão. A tipografia é sans-serif contemporânea — resolve bem legibilidade mas não carrega personalidade gastronômica.

A distância entre os dois não é enorme — o dark mode acerta a direção. Mas é a diferença entre um restaurante premium e o app de pedido desse restaurante.

## 2. Comparação Restaurante × Sistema

### Onde combinam

**Tom escuro:** o restaurante vive no escuro elegante — ambiente com iluminação pontual, madeira escura, couro escuro. O dark mode do sistema está certo. Mudar para claro seria um erro grave.

**Identidade forte:** o "+54" como identificador numérico é poderoso. O sistema já usa isso no header. Essa decisão está correta e deve ser preservada.

**Foco no produto:** as fotos do Instagram são todas close em comida, sem filtros exagerados. O sistema não polui com elementos desnecessários. Essa contenção visual está alinhada.

### Onde entram em conflito

**Temperatura das cores:** o restaurante vive em âmbar, dourado, ocre, marrom quente. O sistema usa vermelho frio e cinza neutro. São paletas de temperatura opostas — o restaurante é *warm*, o sistema é *cool*.

**Tipografia:** o cardápio físico do +54 usa serifa elegante para títulos (visível nos stories do Instagram — "CARDÁPIO (+54) PARRILLA" em fonte serifada com personalidade). O sistema usa sans-serif genérica. Não é errado, mas não carrega o DNA.

**O vermelho:** o vermelho atual lembra botão de "deletar" de sistema administrativo. O restaurante usa um tom mais quente, próximo de vinho tinto envelhecido, não de sinalização de perigo.

**Textura vs planura:** o ambiente físico tem textura em tudo — madeira com veios, couro com costura, tijolos, plantas. O sistema é completamente plano. Um toque sutil de textura (não literalmente, mas na linguagem visual) faria diferença.

**Preço como destaque:** nos stories do cardápio, os preços aparecem com destaque em dourado/âmbar. No sistema o preço está em `--parrilla-ember` (laranja) que é a decisão mais próxima do certo — mas a intensidade poderia ser maior.

## 3. O DNA do +54 Parrilla

Se o restaurante fosse uma pessoa, seria um **sommelier argentino de 55 anos que trabalha naquele restaurante há 20 anos**.

Ele **fala** com calma, com acento, com precisão. Não usa palavras desnecessárias. Quando recomenda um vinho, é porque conhece. Não tenta impressionar — impressiona sem tentar.

Ele **pisa** devagar, com propósito. Nunca corre. Mas quando você precisa dele, está lá.

Ele **cumprimenta** pelo nome se você já esteve lá antes. Na primeira vez, é caloroso mas discreto — não invasivo.

Ele **serve um vinho** sem fazer cerimônia exagerada, mas com um pequeno detalhe que você nota: a temperatura está perfeita, a taça está seca, ele espera você provar antes de servir.

Ele **entrega a conta** numa pasta de couro sem dizer o valor em voz alta. Discreto. Digno.

Ele **pede desculpas por um atraso** olhando nos olhos, sem inventar desculpa, oferecendo algo concreto. Sem dramaturgia.

**Palavras que definem o DNA:**
- Argentino (não genérico sul-americano)
- Carne, brasa, parrilla (não "comida")
- Caloroso mas não exuberante
- Premium sem ser intimidador
- Masculino mas acolhedor
- Artesanal mas preciso

## 5. As 20 maiores diferenças (da mais para a menos importante)

**1. Temperatura da paleta:** o sistema é cool, o restaurante é warm. Esta é a maior distância emocional.

**2. O vermelho:** `#c0392b` é vermelho de alerta. O restaurante pede um vermelho de brasa — mais para `#9B2335` (vinho escuro) ou um tom entre vermelho e ocre queimado.

**3. Ausência de âmbar/dourado como cor principal de destaque:** o accent atual (laranja `#e67e22`) está na direção certa mas claro demais. Precisaria ser mais rico, mais quente, mais "cobre envelhecido".

**4. Tipografia sem personalidade gastronômica:** uma fonte serifada para títulos e display (não para corpo de texto, que permanece sans-serif para legibilidade) mudaria completamente a percepção.

**5. Fundo sem profundidade:** `#0e0e0e` é preto neutro. Um preto levemente aquecido (`#0f0d0b` — com leve tonalidade marrom) aproximaria do ambiente físico sem sacrificar contraste.

**6. Cards sem elevação percebida:** os cards atuais usam border de 1px como única diferenciação. Um leve calor na cor de fundo do card (`#1a1714` em vez de `#1c1c1c`) criaria profundidade visual.

**7. Botão primário parece sistema:** o CTA principal precisa comunicar ação gastronômica, não submit de formulário. Forma e peso importam tanto quanto cor.

**8. Ausência de hierarquia tipográfica clara:** nome do prato, descrição e preço têm pesos próximos. A diferença entre eles deveria ser mais dramática.

**9. Preço não celebrado:** num restaurante premium o preço não é escondido mas também não é agressivo. No sistema ele aparece igual a qualquer outro texto. Poderia ter mais presença.

**10. Logo "+54" poderia ter mais caráter:** atualmente é texto puro. Uma micro-decisão tipográfica (tracking, peso, proporção) faria diferença.

**11. Ícones genéricos:** os emojis usados (🥩, 🍺) funcionam mas não têm identidade. Ícones customizados ou uma família consistente elevariam o produto.

**12. Estados de loading sem personalidade:** o "Carregando..." é completamente genérico. Uma mensagem com voz do restaurante ("Preparando seu cardápio...") mudaria o tom.

**13. Mensagens de erro sem voz:** "Não foi possível carregar" é linguagem de sistema. O restaurante falaria diferente.

**14. Botão "Continuar" como label genérica:** em cada tela o CTA poderia ter uma voz específica que contextualiza a ação.

**15. Ausência de separadores com personalidade:** os `border: 1px solid` são funcionais mas invisíveis. Uma linha mais fina, em cor levemente aquecida, com espaçamento generoso, communicaria elegância.

**16. Espaçamento interno dos cards:** ligeiramente apertado para um produto premium. Mais espaço interno transmite mais valor.

**17. Barra de navegação de categorias:** pills/chips com borda parecem tabs de sistema. Uma linha inferior como indicador de seleção seria mais elegante.

**18. Header muito funcional:** o header atual é correto mas não tem presença. Poderia ter mais height e respiração.

**19. Ausência de fotografia integrada:** o restaurante é altamente visual (ver Instagram). O sistema atual não usa nenhuma imagem ambiental ou de atmosfera.

**20. Confirmações sem emoção:** "Pedido enviado" poderia ser um momento de pequena celebração visual, não apenas uma mensagem funcional.

## 6. Melhorias de maior impacto

Estas cinco mudanças, sem alterar fluxo ou arquitetura, elevariam drasticamente a percepção:

**1. Trocar a paleta de cores para warm dark**
Fundo de `#0e0e0e` para `#0f0d0b`. Vermelho de `#c0392b` para `#8B1A2B`. Accent de `#e67e22` para `#C17F3A`. Superfície de `#171717` para `#1a1714`. Isso sozinho muda a temperatura emocional do produto inteiro.

**2. Adicionar uma fonte serifada para display**
Apenas para h1, títulos de seção e o "+54". O corpo permanece sans-serif. Uma fonte como *Playfair Display*, *Cormorant Garamond* ou *DM Serif Display* carregaria imediatamente o DNA gastronômico. É uma linha no CSS, não uma refatoração.

**3. Dar mais presença ao preço**
Aumentar o tamanho, mudar para a cor accent e adicionar `font-variant-numeric: tabular-nums` com um peso acima do texto de descrição. O preço num restaurante premium não se esconde — ele justifica a experiência.

**4. Reescrever os microtextos com a voz do restaurante**
"Carregando..." → "Preparando seu cardápio..."
"Confirmar pedido" → "Enviar para a cozinha"
"Pedido enviado" → "Seu pedido está nas mãos da nossa cozinha."
"Pedir conta" → "Solicitar a conta"
Zero esforço técnico. Impacto emocional enorme.

**5. Aumentar o espaçamento interno de todos os cards**
De `padding: 14px` para `padding: 18px 20px`. Mais ar = mais valor percebido. Uma das maneiras mais baratas de parecer premium.

## 7. O que manter

**Dark mode:** absolutamente correto para o DNA do restaurante. Não mudar.

**Cantos retos (`border-radius: 2px`):** a decisão de usar cantos quase retos em vez de pills arredondadas está certa. Combina com a estética industrial/rústica da parrilla.

## 9. Pensando no futuro SaaS

Cada sugestão acima foi deliberadamente desacoplada do +54 Parrilla:

| Sugestão | Reutilizável? | Como tornar reutilizável |
|---|---|---|
| Paleta warm dark | Sim | Tokens no `theme.[restaurantId]` — cada restaurante define seus valores |
| Fonte serifada para display | Sim | `theme.fontDisplay` configurável por restaurante |
| Microtextos com voz | Sim | `config.copy.[key]` por restaurante — strings configuráveis, não hardcoded |
| Padding de cards | Sim | Token `spacing.cardPadding` no design system |
| Cantos retos | Sim | Token `radius.default` — uma cafeteria pode querer `radius.lg` |
| Foto de ambiente | Sim | `config.assets.ambientPhoto` por restaurante |

A regra que emerge é: **qualquer elemento visual que hoje está hardcoded no componente deve migrar para um token ou configuração de restaurante.** O componente renderiza. O restaurante decide como parece.

## 3. Tipografia — Baseada em Evidências

O cardápio físico revela duas famílias:

**Display/Marca:** a escrita cursiva em "Itaim Bibi" e no nome das unidades usa uma fonte script elegante, com personalidade italiana/argentina. Referências próximas: *Playfair Display Italic*, *Cormorant Garamond Italic*, *EB Garamond*.

**Corpo/Cardápio:** a listagem de itens usa uma fonte sans-serif condensada, com muito tracking (espaçamento entre letras). Próxima de *Montserrat*, *Raleway* ou a própria fonte atual do sistema.

**Números/Preços:** os preços no cardápio físico aparecem em peso leve, alinhados à direita, com separação clara do nome do prato. Sugerem `font-variant-numeric: tabular-nums` com peso regular — não bold.

## 4. Materialidade e Textura

O restaurante não tem textura literal na identidade digital (cardápio é limpo). Mas a textura aparece na **linguagem** e na **fotografia**.

Para o sistema, textura não significa gradiente ou noise. Significa:

- **Profundidade entre camadas** — background levemente diferente de surface, diferente de surface elevated
- **Calor nas bordas** — borders levemente aquecidos (`#2A2520`) em vez de cinza neutro
- **Sombras quentes** — `box-shadow` com tom âmbar suavíssimo em vez de preto puro

### Alterações em `app/layout.tsx`

**Contexto:** o Next.js 15 com `next/font/google` injeta fontes de forma otimizada — sem requisição externa em runtime, com fallback automático e exposição via CSS variable.

**Passo 1 — Adicionar imports de fonte no topo do arquivo:**

```typescript
import { Cormorant_Garamond, Inter } from 'next/font/google'

const displayFont = Cormorant_Garamond({
  subsets: ['latin'],
  weight: ['400', '600'],
  style: ['normal', 'italic'],
  variable: '--font-display',
  display: 'swap',
})

const bodyFont = Inter({
  subsets: ['latin'],
  weight: ['400', '500', '600'],
  variable: '--font-body',
  display: 'swap',
})
```

**Passo 2 — Aplicar as variáveis no elemento `<html>` ou `<body>`:**

Localizar o elemento raiz do JSX retornado. Adicionar as classes das fontes:

```typescript
<html lang="pt-BR" className={`${displayFont.variable} ${bodyFont.variable}`}>
```

Se já existir `className` no `<html>`, concatenar com espaço. Não remover classes existentes.

**Passo 3 — Importar os dois arquivos CSS na ordem correta:**

Localizar os imports de CSS no topo do arquivo. Adicionar após o import de `globals.css`, nesta ordem exata:


* `next/font` carrega e otimiza as fontes;
* o tema decide qual fonte ocupa cada papel;

### Alterações em `app/layout.tsx`

**Contexto:** o `next/font/google` carrega as fontes de forma otimizada com self-hosting automático. As variáveis técnicas `--font-loaded-display` e `--font-loaded-body` são expostas pelo Next.js e consumidas pelo tema em `plus54.css`. Os nomes técnicos (`--font-loaded-*`) são diferentes dos nomes semânticos (`--font-display`, `--font-body`) para evitar colisão de cascata.

**Adição 1 — Imports de fonte no topo do arquivo:**

Adicionar após os imports existentes, antes de qualquer outro código:

```typescript
import { Cormorant_Garamond, Inter } from 'next/font/google'

const displayFont = Cormorant_Garamond({
  subsets: ['latin'],
  weight: ['400', '600'],
  style: ['normal', 'italic'],
  variable: '--font-loaded-display',
  display: 'swap',
})

const bodyFont = Inter({
  subsets: ['latin'],
  weight: ['400', '500', '600'],
  variable: '--font-loaded-body',
  display: 'swap',
})
```

**Adição 2 — Imports de CSS na ordem correta:**

Localizar onde `globals.css` é importado. Adicionar os dois novos imports imediatamente após, nesta ordem:

```typescript
import '@/app/globals.css'
import '@/styles/tokens.css'
import '@/styles/themes/plus54.css'
```

Se `globals.css` já é importado, não duplicar — apenas adicionar os dois novos após ele.

**Adição 3 — Aplicar variáveis de fonte no elemento raiz:**

Localizar o elemento `<html>` no JSX retornado. Adicionar as classes das fontes:

```typescript
<html lang="pt-BR" className={`${displayFont.variable} ${bodyFont.variable}`}>
```

Se já existir `className` no `<html>`, concatenar com template literal. Não remover classes existentes.
