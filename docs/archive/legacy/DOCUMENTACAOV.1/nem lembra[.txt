# FRONTEND ARCHITECTURE — V1

**Documento:** `docs/architecture/07_FRONTEND_ARCHITECTURE.md`

**Status:** Arquitetura-alvo

**Versão:** 1.0

---

# Objetivo

Este documento define como o frontend do produto é organizado.

Ele responde:

* onde cada responsabilidade deve existir;
* o que pode ou não ficar dentro de um componente React;
* como separar domínio de interface;
* como manter escalabilidade;
* como evitar acoplamentos;
* como permitir evolução do produto sem reescrever telas.

Este documento é a referência oficial da arquitetura frontend da V1.

---

# Filosofia

O frontend não existe apenas para desenhar telas.

Ele representa o comportamento do Motor de Hospitalidade.

O React é apenas a tecnologia utilizada para apresentar esse comportamento.

Por isso:

```text
Produto

↓

Domínio

↓

Motores

↓

Resolvers

↓

Stores

↓

Componentes

↓

Interface
```

Nunca o contrário.

---

# Objetivos

A arquitetura deve permitir:

* múltiplos restaurantes;
* múltiplas experiências;
* múltiplos temas;
* múltiplos idiomas;
* novas jornadas;
* novos painéis;
* novas estações;
* novas regras;
* sem duplicação de código.

---

# Stack

Frontend:

* Next.js App Router
* React
* TypeScript

Estado:

* Zustand

Estilo:

* CSS Modules / CSS global estruturado

Dados:

* Server Components
* Server Actions (quando fizer sentido)
* Supabase

# Princípio fundamental

Nenhum componente deve conhecer regras do restaurante.

Ele conhece apenas:

```text
ExperienceProfile
```

e

```text
BrandIdentity
```

Todo o restante vem da configuração.

---

# Estrutura de pastas

```text
app/

components/

lib/

hooks/

providers/

styles/

types/

config/

docs/
```

---

# app/

Responsabilidade:

roteamento.

Nada mais.

As páginas apenas:

* carregam dados;
* chamam Gates;
* iniciam Providers;
* renderizam a experiência.

Não colocar regras de negócio.

---

# components/

Responsabilidade:

Interface.

Um componente nunca decide:

* regras;
* fluxo;
* restaurante;
* permissões.

Ele apenas representa estados.

---

## Exemplo

Errado

```tsx
if (restaurant.id === "+54")
```

Correto

```tsx
experience.entry.hero.title
```

---

# lib/

É o coração do sistema.

Tudo que representa domínio fica aqui.

Exemplo:

```text
hospitality/

orders/

session/

menu/

recommendations/

analytics/
```

---

# Engines

Engine representa comportamento.

Exemplo

```text
Hospitality Engine

Recommendation Engine

Routing Engine

Session Engine

Order Engine
```

Engines não desenham interface.

Elas pensam.

---

# Resolver

Resolver transforma dados.

Exemplo

```text
semantic ids

↓

MenuItem real

↓

Experiência pronta
```

Resolver nunca consulta interface.

---

# Stores

Zustand guarda apenas estado do usuário.

Jamais regras.

Exemplo:

```text
mesa

cliente

sessão

preferência

carrinho

tema
```

Não guardar:

```text
cardápio

configuração

catálogo
```

Esses pertencem ao servidor.

---

# Providers

Providers inicializam contexto.

Exemplo

```text
Brand

↓

Experience

↓

Theme

↓

Session
```

Nunca colocar regras de negócio.

---

# Hooks

Responsabilidade:

facilitar consumo.

Nunca implementar lógica pesada.

Exemplo:

```tsx
useCurrentTable()

useCart()

useBrand()
```

---

# Config

Toda personalidade da casa vive aqui.

```text

BrandIdentity

RestaurantProfile
```

O React nunca pergunta:

```text
qual restaurante?
```

Recebe tudo pronto.

Todo componente deve responder:

* configuração;

* animação;

# Erros

# Logs

Logs técnicos ficam apenas em desenvolvimento.

# Testabilidade

Todo Engine deve ser testável sem React.

Todo Resolver deve ser testável sem navegador.

Todo componente deve ser testável isoladamente.

# White Label

Nunca por condicionais.

Correto

```tsx

```

# Critérios de aceite

A arquitetura frontend estará correta quando:

* Nenhum componente depender do restaurante.
* Toda personalidade vier do `ExperienceProfile`.
* Regras estiverem concentradas nas Engines.
* Resolvers transformarem dados, não renderizarem interface.
* Stores armazenarem apenas estado do usuário.
* Gates controlarem acesso sem desenhar telas.
* O App Router servir apenas como fronteira de navegação.
* O Design System permanecer neutro.
* Uma nova marca puder ser adicionada sem alterar componentes React.
* A interface puder evoluir sem modificar a lógica de negócio.
