# ARQUITETURA DE BANCO DE DADOS — V1

**Documento:** `docs/architecture/06_DATABASE_ARCHITECTURE.md`
**Status:** Arquitetura-alvo com evolução incremental
**Versão:** 0.1
**Escopo:** Persistência, relacionamentos, constraints, índices, histórico, idempotência, multiunidade, RLS e estratégia de evolução do banco da V1.

---

## 1. Objetivo deste documento

Este documento define como o domínio operacional deve ser representado no banco de dados.

Ele responde:

* quais informações precisam ser persistidas;
* quais entidades merecem tabelas próprias;
* quais dados podem permanecer derivados;
* como preservar histórico;
* como evitar sessões e pedidos duplicados;
* como separar pedido, produção e entrega;
* como suportar bar, cozinha, garçom e gerente;
* como estruturar múltiplas unidades;
* como aplicar segurança;
* como evoluir o schema sem interromper a operação.

Este documento não representa necessariamente o schema atual já implementado.

Ele diferencia:

```text
Estado atual
→ estruturas já existentes

Estado de transição
→ adaptações necessárias para concluir a V1

Estado-alvo
→ modelo consistente para evolução do produto
```

A implementação deve evoluir gradualmente, preservando dados e comportamento funcional.

---

# 2. Princípios de persistência

## 2.1 O banco representa o estado durável

Informações operacionais confirmadas precisam existir fora do navegador.

Exemplos:

* sessão aberta;
* cliente identificado;
* pedido enviado;
* item em preparo;
* bebida pronta;
* entrega confirmada;
* mesa encerrada.

Não podem depender apenas de:

* Zustand;
* `localStorage`;
* estado de componente;
* eventos realtime;
* memória do servidor.

---

## 2.2 O banco não deve representar detalhes puramente visuais

Não persistir sem necessidade:

* modal aberto;
* posição de scroll;
* animação atual;
* filtro selecionado;
* card expandido;
* tooltip;
* estado de hover.

Esses dados pertencem à interface.

---

## 2.3 Histórico precisa ser preservado

Alterações futuras do catálogo não podem modificar pedidos antigos.

Exemplo:

```text
Hoje:
Bife de Chorizo — R$ 139

Amanhã:
Bife de Chorizo — R$ 149
```

Pedidos realizados hoje precisam continuar exibindo:

```text
R$ 139
```

Por isso, itens enviados devem preservar snapshots comerciais mínimos.

---

## 2.4 Identidade técnica não deve depender de nomes

Não usar nome como chave definitiva para:

* produtos;
* categorias;
* estações;
* unidades;
* mesas;
* funcionários.

Nomes podem mudar.

IDs e chaves estáveis permanecem.

---

## 2.5 Relações operacionais devem ser explícitas

Evitar dependência de inferência.

Exemplo incorreto:

```text
Categoria = Bebidas
→ então destino = bar
```

Exemplo correto:

```text
Produto possui production_station_id
```

ou estrutura equivalente.

---

## 2.6 Dados derivados não precisam ser duplicados

Exemplo:

```text
Mesas ocupadas
```

pode ser calculado pelas sessões ativas.

Não precisa obrigatoriamente existir como coluna atualizada manualmente.

Duplicar estados derivados aumenta o risco de inconsistência.

---

# 3. Tecnologia de persistência

A V1 utiliza conceitualmente:

```text
PostgreSQL
+
Supabase
```

Responsabilidades:

* banco relacional;
* constraints;
* transações;
* índices;
* RLS;
* funções;
* triggers controlados;
* realtime;
* autenticação futura;
* armazenamento de imagens.

O frontend não deve conhecer detalhes internos do schema além das fronteiras de acesso definidas.

# 4. Organização por schema

A V1 pode continuar utilizando o schema:

```text
public
```

Porém, a arquitetura futura pode separar:

```text
public
auth
storage
audit
```

Possível organização futura:

```text
public
→ entidades do produto

audit
→ eventos e histórico operacional

private
→ configurações internas e dados sensíveis
```

Não criar separações de schema apenas por estética.

Elas devem possuir propósito real de segurança, organização ou manutenção.

## Responsabilidade

Representar a organização ou marca proprietária da operação.

## Campos sugeridos

```text

name
slug
status
created_at
updated_at
```

Possíveis estados:

```text
active
inactive
suspended
```

## Regras

* `slug` deve ser único.
* Não armazenar toda configuração white-label em colunas dispersas.
* Identidade pode ser vinculada por configuração estruturada ou tabela própria futura.
* Exclusão física deve ser evitada quando existirem dados históricos.

# 9. `table_sessions`

## Responsabilidade

Representar uma visita específica em uma mesa.

É uma das tabelas mais importantes da arquitetura.

## Campos sugeridos

```text
id
unit_id
table_id
status
party_size
opened_at
closing_requested_at
closed_at
created_by
created_at
updated_at
version
```

## Estados

```text
opening
active
closing
closed
cancelled
error
```

## Constraints

```text
party_size >= 1
```

## Sessão ativa única

Garantir no banco que uma mesa não tenha duas sessões operacionais simultâneas.

Exemplo conceitual com índice parcial:

```sql
CREATE UNIQUE INDEX unique_active_table_session
ON table_sessions (table_id)
WHERE status IN ('opening', 'active', 'closing');
```

Essa regra é crítica.

Proteção apenas no frontend não é suficiente.

## Regras

* `table_id` é preferível a depender apenas de `table_num`.
* `unit_id` pode parecer redundante, mas facilita segurança e consultas.
* Uma sessão encerrada não deve ser reativada silenciosamente.
* Reabertura precisa ser uma operação explícita e auditada.
* `version` pode apoiar concorrência otimista.


# 28. JSONB: quando usar

JSONB é adequado para:

* configurações flexíveis;
* metadata;
* payloads de eventos;
* preferências;
* dados experimentais;
* conteúdo white-label;
* opções que variam entre estabelecimentos.

Exemplos:

```text
units.settings
production_stations.settings
menu_items.metadata
operational_events.payload
```

---

# 29. JSONB: quando não usar

Não usar JSONB como substituto permanente de relações importantes.

Evitar guardar apenas em JSON:

* itens do pedido;
* estado por item;
* destino operacional;
* produção;
* entrega;
* participantes;
* tarefas;
* atribuições.

Problema:

```text
orders.items JSONB
```

é simples no início, mas dificulta:

* constraints;
* atualização individual;
* realtime por item;
* índices;
* produção parcial;
* cancelamento individual;
* entrega individual;
* relatórios;
* auditoria.

---

# 30. Estratégia de migração do JSON de pedidos

Caso a implementação atual use:

```text
orders.items JSONB
```

A evolução deve ser gradual.

## Fase 1 — Preservar compatibilidade

Criar `order_items` e continuar lendo pedidos antigos pelo JSON.

Novos pedidos passam a gravar em ambas as estruturas temporariamente, se necessário.

---

## Fase 2 — Backfill

Converter pedidos históricos:

```text
orders.items
→ order_items
```

Registrar inconsistências.

Não inventar dados ausentes.

---

## Fase 3 — Fonte principal relacional

Novos fluxos usam apenas `order_items`.

O JSON pode continuar como snapshot legado somente para leitura.

---

## Fase 4 — Remoção futura

Remover dependência do JSON após:

* validação;
* backups;
* comparação de resultados;
* ausência de consumidores legados.

Não remover campo diretamente na V1 sem necessidade.

# 31. Chaves primárias

Preferência conceitual:

```text
UUID
```

para entidades distribuídas e expostas externamente.

Porém, o projeto atual pode usar IDs numéricos.

Ambos são válidos.

Critérios:

## IDs numéricos

Vantagens:

* simples;
* compactos;
* rápidos;
* fáceis de depurar.

Riscos:

* enumeráveis;
* mais cuidado em APIs públicas;
* conflito em importações externas.

## UUID

Vantagens:

* geração distribuída;
* menor risco de enumeração;
* útil em idempotência.

Riscos:

* maior tamanho;
* logs menos legíveis.

Não migrar todos os IDs apenas por preferência estética.

Essas chaves não substituem a primary key.

Servem para:

* configuração;
* white label;
* curadoria;
* importação;
* integração.

Evitar registros órfãos.

# 34. Estratégia de exclusão

Não usar `CASCADE` indiscriminadamente em dados operacionais.

Exemplo perigoso:

```text

→ apagar sessões
→ apagar pedidos
→ apagar histórico
```

Preferir:

* inativação;
* soft delete;
* bloqueio de exclusão;
* arquivamento.

## Inadequado como única estratégia para

Não usar:

# 39. Quantidade

Quantidade de itens:

```text

```

```text

```

Caso produtos fracionáveis existam futuramente, avaliar:

```text

```

Mas não generalizar antes da necessidade.

# 40. Versionamento de registros

Entidades operacionais sujeitas a concorrência podem possuir:

```text
version integer
```

A cada atualização:

```text
version = version + 1
```

Mutação condicional:

```text
UPDATE ...
WHERE id = ?
AND version = ?
```

Isso evita sobrescrita silenciosa.

Prioridade para:

* pedidos;
* itens;
* produção;
* entrega;
* solicitações;
* sessões.

# 41. Idempotência

Operações críticas devem possuir chave idempotente.

Exemplos:

```text

service_requests.idempotency_key
```

## Constraint

```text
UNIQUE (unit_id, idempotency_key)
```

ou escopo equivalente.

## Regras

* Retry usa a mesma chave.
* O servidor retorna operação existente.
* A chave deve possuir contexto suficiente.
* Não confiar somente no Zustand.
* Não confiar somente em memória de uma instância.

# 52. Segurança por linha — RLS

A RLS deve refletir o papel e o escopo.

## Cliente

Pode ler:

* sua sessão;
* seus pedidos;
* informações públicas do catálogo;
* status relevantes.

Pode criar:

* pedidos na sessão ativa;
* solicitações;
* identificação própria.

Não pode:

* ler outras mesas;
* alterar produção;
* alterar preços;
* fechar sessão diretamente sem regra.

---

## Bar

Pode ler:

* tarefas da estação bar da unidade;
* contexto mínimo da mesa;
* observações necessárias.

Pode atualizar:

* tarefas sob sua responsabilidade.

Não pode:

* editar catálogo;
* acessar dados de pagamento;
* alterar outras estações.

---

## Cozinha

Mesmo princípio, escopo `kitchen`.

---

## Garçom

Pode ler:

* mesas permitidas;
* entregas;
* solicitações;
* pedidos necessários ao atendimento.

Pode atualizar:

* entregas;
* solicitações;
* fechamento permitido.

---

## Gerente

Pode ler a operação completa da unidade.

Pode executar intervenções autorizadas.

---

## Administrador

Pode configurar o restaurante/unidade no escopo autorizado.

# 72. Realtime e tabelas

* table_sessions;
* customer_sessions;
* orders;
* order_items;
* production_tasks;
* delivery_tasks;
* service_requests;
* operational_alerts.

Não habilitar realtime indiscriminadamente em tabelas administrativas.

---

# 73. Payload realtime

Quanto mais larga a tabela, maior o payload.

Evitar colocar grandes estruturas em registros frequentemente atualizados.

Exemplo problemático:

```text
orders.items JSONB muito grande
```

Toda atualização retransmite o registro inteiro.

A normalização reduz payload e melhora granularidade.

# 74. Integridade entre pedido e sessão

Ao criar pedido:

* sessão precisa existir;
* sessão precisa estar ativa;
* unidade precisa corresponder;
* mesa precisa corresponder;
* cliente precisa pertencer à sessão;
* produto precisa pertencer à unidade;
* estação precisa pertencer à unidade.

Essas regras precisam ser validadas no servidor ou função transacional.

---

# 75. Integridade entre item e estação

O item deve herdar inicialmente a estação do produto.

Mas o snapshot precisa ser preservado:

```text
order_items.production_station_id
```

Se o produto mudar de estação depois, pedidos antigos não mudam.

---

# 76. Integridade entre produção e entrega

Somente uma tarefa de produção pronta pode liberar entrega.

Exceções:

* item de serviço;
* item que não exige produção;
* entrega direta.

Esses casos devem possuir rota explícita.

Exemplo:

```text
service
→ ServiceRequest
```

não precisa gerar `ProductionTask`.

---

# 77. Estado agregado do pedido

Duas opções:

## Derivado sempre

Calcular pelos itens.

Vantagem:

Desvantagem:

## Cache controlado

Persistir `orders.status`.

Atualizar transacionalmente com os itens.

Vantagem:

* leitura rápida.

Desvantagem:

* risco de divergência.

Recomendação para V1:

```text
status cacheado

recalculável
+
validado por testes
```

* limpar ou arquivar pedidos artificiais;
* preservar somente cenário demonstrativo intencional;
* não mostrar nomes como “Teste PATCH”.

O painel do gerente precisa parecer uma operação real.

---

# 85. Critérios de aceite do banco da V1

A arquitetura de dados da V1 estará adequada quando:

1. a mesma mesa não tiver sessões ativas duplicadas;

2. pedidos incrementais pertencerem à mesma sessão;

3. bebidas forem roteadas ao bar;

4. comida for roteada à cozinha;

5. itens estiverem preservados historicamente;

6. retries não duplicarem pedidos;

7. produção e entrega puderem ser distinguidas;

8. cliente não acessar outra mesa;

9. gerente enxergar a unidade inteira;

10. estados forem consistentes entre painéis;

11. sessão encerrada não aceitar pedidos;

12. catálogo puder ser editado sem alterar histórico;

13. produtos puderem ser desativados sem exclusão;

14. dados de teste puderem ser isolados;

15. migrations forem seguras e reversíveis.

# 86. Decisões que exigem auditoria do projeto

* schema atual;
* constraints;
* índices;
* triggers;
* RLS;
* tipos reais;
* dependências;
* foreign keys;
* funções;
* uso de IDs;
* consumidores de JSON;
* políticas realtime;
* dados existentes.

Não criar schema baseado apenas neste documento.

Este documento define o estado desejado.

A implementação deve respeitar o estado real.
